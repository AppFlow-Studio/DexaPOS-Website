## C3 — `replaceDoc` marks the server's own document dirty

### Root cause

[`store.ts:499-508`](../../../components/site-builder/builder/store.ts#L499-L508) sets `saveState: "dirty"`
unconditionally. It was written when two callers existed: a starter-template load (legitimately dirty) and
conflict resolution (legitimately clean). **The template caller is gone.** `grep` finds one call site:

- [`BuilderShell.tsx:306`](../../../components/site-builder/builder/BuilderShell.tsx#L306) — the conflict
  toast's *"Load theirs"*.

So the flag is now wrong on every invocation. What follows from one click of "Load theirs":

1. `saveState` becomes `"dirty"`, so `useAutosave` schedules a flush 1.5 s later.
2. That flush writes the server's own content back to the server and bumps `revision` for nothing.
3. `saveError` is still `"This page was changed in another window."` — it is never cleared, because only
   `markSaved` clears it and `markSaved` is not on this path.
4. `useSaveFailureToast`'s `announced` ref only resets on `saveState === "saved"`, which never happens.
   A genuine later save failure is therefore announced **once at most for the rest of the session**.

(3) and (4) are new observations from the verification pass; the original finding covered only (1)–(2).

### The fix

Adopting the server's document means the local document *is* the stored one. There is nothing to save, no
error outstanding, and no reason to schedule a write. Rename the action to say so, and set the terminal
state directly.

```ts
/** Adopts the stored document wholesale — conflict resolution's "Load theirs". */
adoptServerDoc: (doc: PageDocument, revision: number) =>
  set((state) => ({
    doc,
    revision,
    past: [...state.past, state.doc].slice(-HISTORY_LIMIT),
    future: [],
    selectedId: null,
    saveState: "saved",
    saveError: null,
    editGeneration: state.editGeneration + 1,
    coalesceKey: null,
  })),
```

Notes on the choices, since each is load-bearing:

- **`revision` is required now, not optional.** The old signature allowed omitting it, which on this path
  would have kept the stale revision and guaranteed a second conflict. No caller omits it; making it
  required removes the trap.
- **`past` still receives the merchant's version.** "Load theirs" discards their work. There is no undo
  button any more, but the entry costs nothing and is the only trace of what was replaced.
- **`editGeneration` still increments.** The document genuinely changed. If a save were somehow in flight,
  `markSaved`'s generation check would then correctly decline to call it saved — the guard works *because*
  we bump.
- **`saveState: "saved"` is what stops the redundant write**, and clearing `saveError` is what re-arms the
  failure toast for the rest of the session.

## C4 — `normalizePage` emits props its own schema rejects

### Root cause, restated

The audit's title says a location binding is "wiped". Reading the code, that is not what happens —
`pickValidFields` re-parses each field independently and keeps every valid one, so a good `location` key
always survives. The binding is only replaced when it was **already** missing or invalid.

The actual defect is one line up:

```ts
props = { ...def.defaults(), ...pickValidFields(def.schema, clampedProps) };   // normalize.ts:187
```

`def.defaults()` with no context returns `locationDefaults("")`, i.e. `{ type: "location", id: "" }`. And
`bindingSchema` is:

```ts
id: z.string().min(1).max(64),   // bindings/types.ts:63
```

So **`normalizePage` produces a section whose props fail its own schema.** That breaks the contract stated
in `normalize.ts`'s own header — *"nothing downstream should defend against malformed sections, because
nothing downstream ever sees one."* Three consequences, in ascending order of how much they hurt:

1. The page cannot be published — `validate.ts:135` raises the blocking `unset_binding`.
2. `normalizePage` is not idempotent on this document. The whole-object parse fails again on every call,
   so the repair path re-runs and re-reports `invalid_props` — on every `renderCanvas`, every draft load,
   every publish attempt.
3. **The section stops accepting edits.** `updateSectionProps` builds
   `candidate = { ...section.props, ...patch }` and re-parses the whole object
   ([`mutations.ts:282`](../../../lib/site-builder/mutations.ts#L282)). With `id: ""` sitting in props,
   *every* patch that does not itself set `location` is refused — "Show map", the heading, the map style.
   The merchant meets a section that has silently stopped responding.

Recovery does exist: the publish blocker's "Fix it" selects the section, and the location ref control offers
**"Link to this restaurant"** ([`SectionDrawer.tsx:1113`](../../../components/site-builder/builder/SectionDrawer.tsx#L1113)),
whose patch *does* include `location` and therefore passes. But the merchant only finds it by being blocked
first, and only after everything else they tried was refused.

### Why the audit's suggested fix cannot work on its own

> *"Fixing this means threading a `SectionDefaultsContext` through `normalizePage`."*

It does not, for two independent reasons:

1. **Two of the six call sites have no location id in scope.**
   `normalizePageWithReport` is called from `draft.ts` (×4 — `LoadDraft`, `SaveDraft`, the conflict re-read,
   `OverwriteDraft`), `publish.ts` (×2), `render-canvas.tsx`, and `built-site.tsx` (×2). `draft.ts` and
   `publish.ts` take `(clerkOrgId, pageId)` and nothing else. Giving them a location id means adding a
   `loadSiteContext` round trip to `SaveDraft` — which is on the autosave hot path, called every 1.5 s
   while a merchant types. That is a real cost to fix a repair-path edge case.
2. **Even with perfect context, a fallback is still required.** A merchant can have no online store
   configured for the location, and `built-site.tsx` renders pages for sites whose location may have been
   removed. Something must be storable when there is no id, and today that something is invalid.

Threading context is therefore an *enhancement* (it avoids the blocker in more cases), never the fix.
The fix has to make the unset state legal.

### The fix: let the schema store it, let the publish gate refuse it

Drop `.min(1)` from the binding id.

```ts
// bindings/types.ts
export function bindingSchema<T extends BindingType>(type: T) {
  return z.object({
    type: z.literal(type),
    // Deliberately allows "". An unset binding is a legal state of a DRAFT — a
    // section added before its subject is chosen, or one repaired from a
    // document that never had a valid id. It is not a legal state of a
    // PUBLISHED page, and `validate.ts` is what refuses it there
    // (`unset_binding`, a blocking error, for every binding type at any depth).
    // Enforcing it here instead froze the section against every other edit,
    // because `updateSectionProps` re-parses the whole props object.
    id: z.string().max(64),
    overrides: bindingOverridesSchema,
  });
}
```

**This is a split of responsibility, not a loosening of the rules.** The schema answers "what may be stored
in a draft"; `validate.ts` answers "what may go live". The non-empty rule already lives in the second place
and is *stricter* there than the schema was — `collectSectionBindingIds`
([validate.ts:290](../../../lib/site-builder/validate.ts#L290)) walks props to any depth, through arrays,
and raises `unset_binding` for every binding type. Nothing becomes publishable that was not publishable
before.

**Blast radius is three fields**, all covered by that gate:

| Field | File |
|---|---|
| `location` | [`schemas/location.ts:18`](../../../lib/site-builder/sections/schemas/location.ts#L18) |
| `location` | [`schemas/footer.ts:12`](../../../lib/site-builder/sections/schemas/footer.ts#L12) |
| `items[]` (menu_item) | [`schemas/popular-items.ts:20`](../../../lib/site-builder/sections/schemas/popular-items.ts#L20) |

**Resolution already tolerates it.** `resolveBindings` looks ids up in a `Map` and records
`unavailable("not_found")` for a miss ([resolve.ts:151-153](../../../lib/site-builder/bindings/resolve.ts#L151-L153)) —
no throw, and the renderer already handles the unavailable case.

What each consequence becomes:

1. Publish still blocked — unchanged, and correct: the page genuinely has no restaurant linked.
2. `normalizePage` becomes idempotent. The repaired props now parse, so the second pass takes the success
   branch and records no repair.
3. **The freeze is gone.** Every other edit to the section is accepted again, and "Link to this restaurant"
   goes from the only possible edit to one of many.

### The guard that stops this class of bug recurring

The bug is a default that its own schema rejects. That is checkable for every section at once:

```ts
// registry.test.ts
it.each(Object.keys(SECTION_REGISTRY))("%s: context-free defaults satisfy their own schema", (kind) => {
  const def = SECTION_REGISTRY[kind];
  expect(def.schema.safeParse(def.defaults()).success).toBe(true);
});
```

Worth more than the fix itself — it is the invariant `normalize.ts` has always assumed and never asserted.

**Measured, not assumed** (see [Probe results](#probe-results)): exactly two kinds fail it today —
`location` and `footer` — and the one-line fix takes that to zero. No other kind is affected, so this test
adds no scope.

## Order, and what is deliberately not here

**Do C3 first.** It is self-contained, touches one file plus its caller, and carries no schema risk. C4
touches a shared validator and wants its invariant test landed carefully.

Explicitly out of scope, deferred with reasons:

| Item | Why not now |
|---|---|
| **Threading `SectionDefaultsContext`** | An enhancement on top of the C4 fix, not a substitute — see above. Costs a round trip on the autosave path. Revisit only if merchants actually hit the blocker. |
| **Recovering a location id from elsewhere in the document** (a two-pass normalize that harvests a valid `{type:"location",id}` from any section and uses it as the defaults context) | Genuinely elegant — no signature change, no query, works at every call site. But it is an optimisation of an edge case, and it should land *after* the invariant is restored, not instead of it. |
| **U4 (`"New"` repeater rows)** | Same underlying invariant as C4 — "incomplete but editable" — so it gets cheaper once C4 lands. Separate change. |
| **I1 (silent blank canvas)** | Next in priority after these two, but unrelated in mechanism. Own change. |
| **C5** | Folded into C3 only if it is a few lines; otherwise dropped as cosmetic. |
| **P3's remaining half** | A narrower menu query, not a cache. Its own piece of work. |
